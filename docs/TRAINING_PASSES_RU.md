# Абонементы и посещаемость

## Использование

- Взносы → Абонементы: выдача пакета (4/8/12 или своё число от 1 до 1000) либо безлимита. Стоимость, начало и окончание включительно задаются при выдаче. Оплата подтверждается вручную.
- В карточке игрока администратор видит его абонементы. Авторизованный участник видит только свои абонементы в личном профиле.
- Событие типа «Тренировка» → Посещаемость: присутствовал, отсутствовал, сбросить. Отметки доступны после начала события.
- При присутствии автоматически выбирается оплаченный, незамороженный, незакрытый абонемент, действующий на дату тренировки. При нескольких абонементах выбирается ближайший по окончанию срока, затем по ID. Остаток должен быть положительным; безлимит не ограничивает число посещений.
- Если подходящего абонемента нет, присутствие фиксируется как разовое посещение. Учёт разового взноса остаётся в существующем расчёте события; журнал сам не добавляет игрока в голосование и не формирует новое начисление.
- Неоплаченный/замороженный подходящий абонемент блокирует списание с понятной ошибкой. Если есть другой подходящий оплаченный абонемент, используется он.
- Повторная одинаковая отметка ничего не списывает. Сброс или изменение на «Отсутствовал» возвращает посещение. Если абонемент выдан после отметки разового посещения, сбросьте и повторно отметьте присутствие.
- Заморозка блокирует новые списания. При снятии срок продлевается на число календарных дней заморозки в часовом поясе организации. «Продлить срок» добавляет дни, но не занятия; новый пакет выдаётся отдельным абонементом.
- При отмене/деактивации события занятия возвращаются транзакционно триггером БД, в том числе при отмене планировщиком. При восстановлении события посещаемость требуется отметить заново.
- Абонемент покрывает одно место самого игрока. Гости оплачиваются отдельно. Если разовая оплата уже полностью отмечена, сначала необходимо отменить её отметку для использования абонемента.
- В истории сохраняются выдача, изменения статуса/срока и списания/возвраты. Закрытие сохраняет историю и не выполняет денежный возврат.
- «Скоро заканчиваются» и «Пора продлить» — подсказки в интерфейсе. Автоматические сообщения в Telegram и эквайринг в эту версию не входят.

## Данные и права

Миграции 00040 и 00041: training_passes, training_attendance, training_pass_history, представление event_effective_payments и cash_amount_paid. Исходные денежные записи сохраняются, представление учитывает покрытие абонементом. Дополнительная миграция 00041 обновляет уже установленное первоначальное представление и сохраняет суммы денежных оплат при возврате посещения.

Все операции управления используют существующее право roles_manage, как раздел взносов. /passes/mine использует profile_read и ID из авторизованной сессии. При отключённой локальной авторизации личный список пуст.

API: GET/POST /api/groups/:chatID/passes; PATCH /passes/:id; GET /passes/mine; GET/PUT /api/groups/:chatID/attendance/:instanceID. Фильтр userID на общем списке доступен только администраторам.

Выдача идемпотентна по UUID запроса. Изменения абонемента проверяют версию. Записи посещаемости и оплаты синхронизированы блокировкой организации; событие блокируется на время отметки, чтобы отмена не потерялась. Количество использованных занятий вычисляется по журналу.

## Проверка

`go test ./internal/storage/postgres ./internal/web` проверяет правила состояния и защиту маршрутов от неавторизованных запросов.

При TEST_DATABASE_URL (PostgreSQL URL) дополнительно запускается интеграционный тест в отдельной временной схеме: все миграции, повторная выдача, конкурентное списание последнего занятия, изоляция организаций, гости и частичная денежная оплата, возврат/отмена, заморозка, версии, неоплаченные и безлимитные абонементы. Тестовая схема удаляется после проверки; данные организации не затрагиваются.

Перед запуском обновлённого API необходимо применить миграции до версии 41. Затем собрать web и перезапустить только нужный сервис. Frontend: `npm run build`.
